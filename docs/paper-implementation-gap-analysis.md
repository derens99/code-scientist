## Bottom Line

Code Scientist currently replicates the paper's control-loop shape, not the paper's full behavior.

The implementation has a useful local MVP: structured run state, plan configuration, deterministic hypothesis generation, review/ranking/evolution agent classes, Elo matches, lexical proximity edges, meta-review feedback, context snapshots, resume/continuous run support, safety gates, reports, and a Next.js workbench for starting and inspecting runs.

It is not yet a close replication of the AI co-scientist system described in the paper. The missing layer is the real agentic substrate: full grounded literature/tool use, asynchronous weighted workers, multi-turn scientific workers beyond pairwise ranking, deep verification reviews, semantic proximity, human feedback injection, richer context memory, systematic safety red-teaming, and serious evaluation against coding-agent benchmarks and human preferences.

Completion estimate: about 67% complete relative to the PDF as an engineering replication. The implementation has much of the control-loop, state, retrieval, workbench, plan-governed source/tool selection, safety-governance, citation-audited reporting, and evaluation substrate, but it is still materially incomplete as a paper-faithful co-scientist because real human/external validation, production-scale benchmark studies, broader governed retrieval/tool integrations, and deeper live multi-turn scientific workers are not finished.

## Paper Requirements

The paper's technical system requires these major mechanisms:

1. A natural-language scientist interface that can accept goals, constraints, preferences, feedback, manual reviews, and user-supplied hypotheses.
2. A research plan configuration parsed from the goal, including proposal preferences, constraints, and evaluation criteria.
3. An asynchronous task framework where a supervisor assigns specialized agents to worker processes and allocates compute.
4. Persistent context memory storing system state, progress statistics, feedback, and restartable agent state.
5. Specialized agents:
   - Generation: literature exploration, simulated debate, assumptions decomposition, research expansion.
   - Reflection: initial review, full review, deep verification, observation review, simulation review, recurrent tournament review.
   - Ranking: Elo tournament with pairwise comparisons and scientific debate.
   - Proximity: goal-aware relatedness graph for clustering, deduplication, exploration, and scheduling.
   - Evolution: grounding, feasibility, analogies, combination, simplification, and divergent thinking.
   - Meta-review: recurring critique synthesis, prompt feedback, research overviews, publication/grant formatting, contact identification.
6. Tool use for web search, retrieval, private publication repositories, domain databases, and specialized AI models.
7. Expert-in-the-loop operation, with scientists making final decisions.
8. Safety controls at goal, hypothesis, monitoring, logging, and red-team levels.
9. Evaluation beyond unit tests: Elo calibration, test-time compute scaling curves, baseline comparisons, expert preference studies, adversarial safety evaluations, and external validation.

## Paper-To-Code Findings

### 1. The data model is close enough for an MVP, but too thin for the paper

Current `RunState` has the right top-level shape: goal, plan, evidence, hypotheses, reviews, matches, proximity edges, benchmark results, meta-reviews, context snapshots, and safety. This is the strongest part of the implementation.

The gap is that most fields are summaries rather than first-class scientific artifacts. A paper-faithful system needs richer records:

- `ResearchPlanConfig` should include parsed user preferences, required output formats, source constraints, allowed tools, review rubrics, termination criteria, and per-agent budget weights.
- `Review` should encode review type, cited evidence, assumption checks, novelty findings, contradiction findings, and confidence.
- `Match` should store debate transcript or judge reasoning, compared reviews, comparison mode, uncertainty, and optional tie/abstain.
- `ProximityEdge` should include a reason, cluster label, and method metadata.
- `MetaReview` should include agent-specific feedback and a research overview, not only weakness counts.
- `Evidence` should represent retrieved papers, code observations, benchmark artifacts, user feedback, and external tool results with citations and provenance.

### 2. The supervisor executes a fixed sequence, not a weighted task framework

The paper's supervisor assigns specialized agents to workers according to task queue priorities and resource weights. Current Code Scientist always follows a fixed sequence:

1. Generate up to a calculated limit.
2. Review generated hypotheses.
3. Compute proximity.
4. Run up to `max_matches` pairwise matches.
5. Evolve top two leaders if capacity remains.
6. Meta-review.
7. Persist a context snapshot.

That sequence is useful and testable, but it does not yet use `scheduler_weights` to choose work. The weights are persisted and adjusted in context snapshots, but they do not schedule actual worker tasks.

To replicate the paper, develop a task model such as:

- `Task(id, run_id, kind, priority, payload, status, attempts, created_at, updated_at)`
- task kinds: `generate`, `review_initial`, `review_full`, `review_deep`, `review_observation`, `rank_pair`, `compute_proximity`, `evolve`, `meta_review`, `render_overview`, `tool_search`, `user_feedback_ingest`
- priority policy driven by plan weights, age, match coverage, hypothesis Elo, proximity cluster coverage, safety state, and missing evidence.
- async workers with bounded concurrency and persisted task states.

### 3. The agents exist as classes, but most are deterministic placeholders

The class boundaries match the paper, which is good. The behavior is not yet close:

- Generation has hardcoded blueprints and an optional single-shot JSON LLM call.
- Reflection is rule-based and does not inspect external evidence.
- Ranking chooses by a simple structural score, not by debate or a judge model.
- Evolution can now generate deterministic evidence-grounded, simplification, feasibility, feedback-grounded, combination, analogy, and divergent variants, but it is still not a deeper tool-using evolutionary worker.
- Proximity is lexical token overlap.
- Meta-review counts repeated weakness strings.

This is acceptable for an auditable MVP, but it should be named and treated as a scaffold. A paper-faithful next version should implement LLM-backed, schema-validated agents with the prompts and review modes from the appendix, plus deterministic fallbacks for tests.

### 4. Literature and tool grounding are the largest missing capability

The paper repeatedly depends on web search, article retrieval, private publication repositories, open databases, and specialized AI models. Code Scientist now has opt-in explicit URL fetching for web evidence, bounded same-origin crawling from explicit URLs, gated Bing RSS web-search result ingestion, opt-in first-hop fetching of web-search result pages, bounded same-origin crawling from those fetched search-result pages, gated OpenAlex works search for literature metadata/abstract evidence, opt-in OpenAlex open-access full-text fetching, and reusable local evidence indexes, but it still lacks broader governed crawling, complete publication repositories, open database adapters, and specialized tool/model integrations for its own domain.

For this repo's domain translation, "literature and tools" should mean:

- Search and retrieval over papers about coding agents, LLM evaluation, self-refinement, agent memory, tool use, SWE-bench-style evaluation, and LLM-as-judge reliability.
- Local repository and transcript retrieval for observed agent failures.
- Benchmark fixture ingestion from real runs rather than hand-written metric JSON only.
- Tool adapters for running coding-agent evaluations and summarizing failures.
- Citation storage with enough provenance to audit claims.

Without the broader retrieval stack, generated hypotheses are still not grounded in prior evidence in the way the paper requires.

### 5. The current workbench is an inspector, not the paper's collaboration interface

The Next.js workbench is useful. It can start local runs, choose provider, configure cycles/matches/hypotheses, browse persisted state, show ranked hypotheses, show matches/meta-review/plan/benchmarks/report, and control continuous runs.

The paper's scientist-in-the-loop interface needs more:

- Add a hypothesis manually.
- Add a manual review for a hypothesis.
- Refine the research goal mid-run.
- Add or remove constraints and evaluation criteria.
- Direct follow-up toward a specific cluster or source set.
- Attach or select a private source corpus.
- Mark a hypothesis as selected, rejected, needs verification, or experimentally validated.
- Record human preference rankings for evaluation.

Until those exist, the UI is a local run workbench, not an AI co-scientist collaboration surface.

### 6. Evaluation is currently project health verification, not co-scientist capability validation

The repo is testable: 278 backend tests and 23 web tests pass, and smoke runs produce expected state. That proves the implementation works as software.

It does not prove the generated hypotheses are good. The paper uses several stronger evaluation paths:

- Elo concordance with task correctness.
- Test-time compute scaling across many research goals.
- Comparisons with frontier model baselines and human expert guesses.
- Expert preference ratings for novelty and impact.
- Adversarial safety evaluation across 1,200 unsafe goals.
- External validation for selected biomedical outputs.

For Code Scientist, the equivalent should be:

- A coding-agent research-goal benchmark set.
- Baseline models and baseline workflows.
- Human review rubric for generated coding-agent improvement hypotheses.
- Retrospective validation against known effective workflow improvements.
- Prospective validation where top hypotheses are implemented and measured on real agent tasks.
- Safety and prompt-injection adversarial suites for coding-agent research objectives.

### 7. Safety is present but far below the paper's bar

The current safety layer blocks obvious risky phrases around self-modification, hidden execution, and unreviewed deployment, quarantines unsafe local/fetched evidence before agent retrieval, and can ask a provider-backed safety critic for structured goal, hypothesis, and evidence decisions. That is a useful baseline.

The paper's safety layer is broader:

- Goal safety review.
- Hypothesis safety review.
- Continuous monitoring through meta-review.
- Explainable recommendations and audit traces.
- Comprehensive logging.
- Red-teaming and adversarial evaluations.
- Human oversight and trusted tester feedback.

Developing this does not require copying biomedical restrictions. It requires a Code Scientist policy covering autonomous code changes, credential handling, repo mutation, exfiltration, live deployments, hidden background actions, benchmark gaming, unsafe advice, and prompt-injection via retrieved sources.
